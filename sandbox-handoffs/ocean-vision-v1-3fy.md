# Handoff: ocean-vision-v1-3fy — Assemble (1,4,120,1080,1920) inference tensor

Status: **closed**, evidence below. Tree left uncommitted per this repo's
conservative git policy — commands to commit are at the bottom.

## What I changed

- `src/ov1/tensor/assemble.py` (new) — `InferenceTensorAssembler`, the class
  that stacks a window of per-frame `[L, a*, b*, DoLP]` planes into the spec
  4.2 `(1, 4, 120, 1080, 1920)` tensor:
  - Downscales each plane to the target resolution with `cv2.resize`
    (`INTER_AREA` when shrinking, `INTER_LINEAR` otherwise — a resampling
    choice, not a calibration constant).
  - Stacks the fixed channel order `[L, a*, b*, DoLP]` (spec 4.2), exposed as
    `CHANNEL_ORDER` and index constants `CHANNEL_L/A/B/DOLP`.
  - Adds the batch dim and returns a `torch.float32` tensor.
  - Attempts `torch.Tensor.pin_memory()` for the Jetson zero-copy handoff;
    catches the `RuntimeError` it raises when there's no accelerator and
    reports `pinned=False` + the caught message via `AssembledTensor`,
    rather than silently returning an unpinned tensor as if pinning had
    succeeded.
  - `FrameChannels.from_lab_and_dolp(lab, dolp, glare_masker=None)` — a
    composition helper matching `dolp.py`'s own module docstring, which
    says glare suppression on the L plane happens "before tensor assembly,
    which happens in ocean-vision-v1-3fy". Optional and unset by default:
    `SpecularGlareMasker` requires a per-site `dolp_threshold`, so a caller
    with no site config gets an unsuppressed L, never an invented threshold.
  - Raises `TensorAssemblyError` (never pads/coerces) on: wrong frame count,
    mismatched plane shapes within a frame, non-2D planes, or non-finite
    values — per this repo's fail-loud rule.
- `src/ov1/tensor/__init__.py` (new) — package exports, matching the
  `ingress`/`preprocess` package pattern already in this repo.
- `tests/test_tensor_assemble.py` (new, 22 tests) — shape/dtype, channel
  order, downscale-matches-direct-`cv2.resize`, validation errors, the
  pinned-memory path, and `FrameChannels.from_lab_and_dolp` (with and
  without a glare masker).
- `tests/test_tensor_no_network.py` (new, 1 test) — patches `socket.socket`
  and `socket.create_connection` to raise, drives `assemble()` (including
  the `pin_memory()` attempt) through it. Matches the existing
  `test_preprocess_no_network.py` / `test_ingress_no_network.py` pattern
  this repo already uses for the ingress → inference path (spec 5.2).
- `pyproject.toml` — added `torch>=2.13.0`, pinned to the **CPU-only**
  wheel via `[tool.uv.sources]` / `[[tool.uv.index]]` pointing at
  `download.pytorch.org/whl/cpu`. `uv add torch` without this pulled the
  default PyPI wheel, which on this environment resolved to the full CUDA
  stack (~1.5GB of `nvidia-*` packages: cublas, cudnn, cusolver, triton,
  etc.) — wrong for this GPU-less container, and not what the Jetson AGX
  Orin target uses either (Jetson runs NVIDIA's own JetPack-built torch,
  not PyPI's desktop/server CUDA wheel). Switched to the 148MB CPU wheel;
  see the comment in `pyproject.toml` for the reasoning.
- `uv.lock` — regenerated by `uv sync` after the above.

## Constants introduced

| Name | Value | Unit | Source |
|---|---|---|---|
| `SPEC_CHANNELS` | 4 | count | Spec 4.2, literal shape |
| `SPEC_TEMPORAL_WINDOW_FRAMES` | 120 | frames | Spec 4.2 / spec 2, literal shape (duplicated from `ov1.ingress.ring_buffer.SPEC_TEMPORAL_WINDOW_FRAMES` rather than imported, to keep `tensor` decoupled from `ingress`; both should be kept in sync if spec 2's frame-count-vs-duration ambiguity, already flagged in `ring_buffer.py`, is ever resolved) |
| `SPEC_HEIGHT` | 1080 | px | Spec 4.2, literal shape |
| `SPEC_WIDTH` | 1920 | px | Spec 4.2, literal shape |
| `CHANNEL_ORDER` / `CHANNEL_L/A/B/DOLP` | `("L","a*","b*","DoLP")` / 0,1,2,3 | index | Spec 4.2, literal channel list |

None of these are calibration knobs — they're the architectural shape
contract with `ocean-vision-v1-133` (the autoencoder), so unlike
`LabNormalizer`'s CLAHE parameters or `SpecularGlareMasker`'s
`dolp_threshold` they have a built-in default (overridable in the
constructor, used by tests to keep synthetic tensors small).

No other constants (no thresholds, no interpolation-algorithm magic numbers
beyond the `INTER_AREA`/`INTER_LINEAR` choice, which is an OpenCV
recommendation, not a tuned number).

## Spec performance targets touched — and what was/wasn't measured

- **250ms inference latency (spec 4.2):** not touched by this bead at all —
  tensor assembly is pre-inference. I did run one **timing observation**,
  not a target-vs-measurement claim: assembling a 120-frame window at real
  spec resolution (`(1,4,120,1080,1920)`, ~4GB float32) took ~4s on this
  container's CPU, with no GPU and no Jetson. That number describes this
  laptop-class container, not the target hardware, and is **not** part of
  the committed test suite (too slow for "tests run in seconds" — see
  below). I did NOT commit any assertion that assembly meets any latency
  budget.
- **FNR/FPR (spec 2):** untouched — this bead does no detection.
- Nothing in this bead measures any spec accuracy/latency target. All of it
  is code-path correctness (shape, dtype, channel order, error handling)
  against synthetic data.

## Test-suite design choices (what's real-scale vs reduced-scale)

- Most tests use small synthetic planes (8×8 to 96×64) and a small target
  resolution/window count, to keep the suite fast and match this
  container's "no ocean footage, small synthetic tensors" constraint.
- `TestSpecConstants.test_assembler_defaults_to_spec_shape` asserts the
  *default* `InferenceTensorAssembler().output_shape` is exactly
  `(1, 4, 120, 1080, 1920)` — the literal spec shape — without allocating
  a multi-GB tensor to do it.
- `TestRealResolutionSmoke.test_downscales_real_4k_frames_to_spec_1080p_shape`
  runs the *actual* downscale path (2160×3840 → 1080×1920) end to end, but
  over 3 frames, not the full 120-frame window, keeping it at ~0.08s. This
  exercises the real resize code path spec 4.2 describes ("downscale 4K
  ingress to 1080p") without the ~4s / ~4GB cost of doing it 120 times. I
  did **not** add a full 120-frame, full-1080p test to the committed suite
  — it ran in ~4s standalone (measured above), which I judged too slow for
  a suite this repo wants to run "in seconds" on every invocation. That
  full-scale run is not part of `unittest discover`; if you want it
  re-verified, the one-off script is in this handoff's shell history
  (build 120 `FrameChannels` at `(2160,3840)`, call
  `InferenceTensorAssembler().assemble(frames)`).

## What I decided not to do, and why

- **Did not implement the raw-sensor → `FrameChannels` glue** (pulling a
  `RingBuffer.window()`, running each pair through `LabNormalizer` /
  `compute_dolp` / `SpecularGlareMasker`, and packaging the result). The
  bead's dependencies (`ocean-vision-v1-bze`, `ocean-vision-v1-3qj`) and
  acceptance criteria are about the tensor-assembly step itself, and no
  bead currently owns that end-to-end wiring or the site-config plumbing
  it needs (where do `clip_limit`/`tile_grid_size`/`dolp_threshold` come
  from at runtime?). Filed as **ocean-vision-v1-0h8**.
- **Did not normalize L/a*/b* (uint8, [0,255]) onto DoLP's ([0,1]) scale.**
  Spec 4.2 specifies channel identity and order, not a normalization
  scheme, and picking one is a modeling decision that belongs with
  `ocean-vision-v1-133`'s training-loop work, not baked silently into
  assembly. Filed as **ocean-vision-v1-3hw** (now a dependency of `133`).
- **Did not resolve the 2 vs 4.1 frame-rate/window-duration ambiguity**
  already flagged in `ring_buffer.py`'s docstring (120 frames = 2s at 60fps
  vs 4s at 30fps) — out of scope here; this bead just reuses the 120-frame
  literal.
- **Did not add a hardcoded default `dolp_threshold` or CLAHE params** to
  `FrameChannels.from_lab_and_dolp` — per this repo's "leave the
  calibration knobs" rule, `glare_masker` is optional and `None` by
  default rather than constructing a `SpecularGlareMasker` with a guessed
  threshold.

## What I could not verify

- **Real Jetson pinned-memory / zero-copy behavior.** This container has no
  CUDA/accelerator (`torch.cuda.is_available() == False`), so
  `tensor.pin_memory()` raises `RuntimeError: Cannot access accelerator
  device when none is available.` every time. `AssembledTensor.pinned` is
  `False` and `pin_skipped_reason` carries that message in every test run
  here. I have **not** verified the pinned path actually succeeds and
  behaves as a fast async-copy source on real Jetson hardware — only that
  the code takes the correct branch and reports honestly when it can't run.
- **Real 4K sensor data / real Lab+DoLP statistics** — everything here runs
  on synthetic uint8/float planes, not ocean footage.
- **Whether `(2160,3840)→(1080,1920)` is the right actual ingress→working
  resolution pair** — spec 4.2 says "4K" and "1080p" in prose; I used the
  common 4K UHD (3840×2160) and 1080p (1920×1080) numbers, but this
  container has no capture backend (`ingress/source.py` has no real driver
  yet) to confirm against actual sensor output.
- **250ms/frame inference budget** — not applicable to this bead, and this
  container has no Jetson to time even the parts that are applicable.
